# CI/CD в Training Center Platform

## Что такое CI/CD?

CI/CD — это подход к разработке, при котором часть работы по проверке, сборке и доставке приложения выполняется автоматически.

Когда разработчик пишет код локально, он может убедиться, что приложение работает именно на его компьютере. Но после отправки изменений в общий проект важно автоматически проверить, что код действительно компилируется, тесты проходят и изменения не ломают остальные части приложения.

Для этого в проекте используется **GitHub Actions**.

В нашем проекте процесс постепенно будет состоять из двух частей:

- **CI (Continuous Integration)** — автоматическая проверка и сборка приложения.
- **CD (Continuous Delivery / Deployment)** — доставка и запуск готового приложения на сервере.

На текущем этапе основная CI-часть уже настроена. CD будет добавляться постепенно.

---

## Как разработчик работает с проектом?

Разработчик не должен писать новую функциональность непосредственно в ветке `main`.

Для задачи создаётся отдельная ветка, например:

```text
feature/payment
feature/course-search
fix/user-registration
```

После завершения работы изменения отправляются в удалённый репозиторий GitHub:

```text
Локальная ветка
      ↓
    commit
      ↓
     push
      ↓
Ветка на GitHub
```

После этого разработчик создаёт **Pull Request в `main`**.

Например:

```text
feature/payment
       ↓
 Pull Request
       ↓
      main
```

Pull Request позволяет проверить изменения перед тем, как они попадут в основную ветку проекта.

---

## Что происходит после создания Pull Request?

Для Pull Request, направленного в `main`, GitHub автоматически запускает наш CI pipeline.

Схематично процесс выглядит так:

```text
Developer
    ↓
feature/*
    ↓
Pull Request
    ↓
GitHub Actions
    ↓
Compile
    ↓
Tests
    ↓
Testcontainers
    ↓
JaCoCo
    ↓
SonarQube
    ↓
Package
    ↓
CI успешно пройден ✅
```

Разработчику не нужно вручную запускать эти проверки на сервере — GitHub Actions делает это автоматически.

## Что проверяет наш CI?

### 1. Compile

Maven компилирует Java-код проекта.

На этом этапе можно обнаружить ошибки компиляции: неправильные типы, отсутствующие классы, некорректные вызовы методов и другие проблемы, из-за которых приложение невозможно собрать.

### 2. Tests

Запускаются автоматические тесты проекта.

Если изменение разработчика нарушило существующее поведение приложения и какой-либо тест перестал проходить, CI завершится с ошибкой.

### 3. Testcontainers

Для некоторых интеграционных тестов недостаточно протестировать отдельный Java-класс.

Например, необходимо проверить взаимодействие приложения с настоящей PostgreSQL.

В таких случаях используется **Testcontainers**. Во время тестирования автоматически запускается временный Docker-контейнер с необходимой инфраструктурой.

Например:

```text
Integration Test
       ↓
Testcontainers
       ↓
PostgreSQL container
       ↓
наш Spring Boot сервис
```

После завершения тестов временный контейнер удаляется.

На текущем этапе интеграционные тесты с Testcontainers добавлены в `auth-service`.

### 4. JaCoCo

**JaCoCo** собирает информацию о покрытии Java-кода тестами.

Он позволяет увидеть, какие классы, методы, строки и ветви кода выполнялись во время тестов, а какие пока остаются без тестового покрытия.

Высокий процент покрытия сам по себе не означает хорошее качество тестов, поэтому JaCoCo используется как дополнительный инструмент анализа, а не как единственный показатель качества.

### 5. SonarQube Cloud

Код проекта анализируется с помощью **SonarQube Cloud**.

Sonar помогает находить потенциальные проблемы в коде, связанные с:

- надёжностью;
- безопасностью;
- поддерживаемостью;
- дублированием кода;
- качеством реализации.

Sonar также может использовать информацию о покрытии, собранную JaCoCo.

### 6. Package

После успешных проверок Maven собирает модули проекта в готовые `.jar`-файлы.

Таким образом CI подтверждает, что текущую версию проекта можно успешно собрать.

## Что означает зелёная или красная проверка?

После создания Pull Request в GitHub отображается результат GitHub Actions.

Если проверки завершились успешно:

```text
Pull Request
     ↓
CI
     ↓
✅ Checks passed
```

значит автоматические проверки не обнаружили ошибок, блокирующих сборку.

Если один из этапов завершился ошибкой:

```text
Pull Request
     ↓
CI
     ↓
❌ Check failed
```

необходимо открыть упавший job в GitHub Actions и посмотреть его лог.

Например, причиной может быть:

```text
Compilation error
Test failed
Integration test failed
Maven build failed
```

Исправление выполняется в той же рабочей ветке. После нового `commit` и `push` GitHub автоматически запустит проверки Pull Request ещё раз.

## Что происходит после Merge?

Если изменения проверены и Pull Request принят, код объединяется с веткой `main`.

```text
feature/*
    ↓
Pull Request
    ↓
CI ✅
    ↓
Merge
    ↓
main
```

Изменение `main` запускает CI ещё раз.

Но для `main` появляется дополнительный этап — создание Docker-образов микросервисов.

```text
main
 ↓
CI
 ↓
Build
 ↓
Docker images
 ↓
GHCR
```

Для сборки нескольких микросервисов используется **matrix strategy GitHub Actions** — отдельные Docker-образы собираются для сервисов проекта.

Готовые образы публикуются в **GitHub Container Registry (GHCR)**.

Таким образом Pull Request используется прежде всего для проверки кода, а Docker-образы публикуются после того, как изменения действительно попали в `main`.

---

## Зачем нужны Docker-образы?

Обычный `.jar` содержит наше Java-приложение.

Docker-образ содержит всё необходимое для запуска конкретного сервиса в стандартизированном окружении, включая приложение и Java Runtime.

Упрощённо:

```text
Spring Boot source code
        ↓
       Maven
        ↓
       JAR
        ↓
      Docker
        ↓
   Docker image
        ↓
       GHCR
```

Позже именно эти Docker-образы будут использоваться для запуска приложения на сервере.

## А где CD?

На текущем этапе мы в основном настроили **CI**.

Сейчас процесс заканчивается примерно здесь:

```text
Developer
    ↓
GitHub
    ↓
Pull Request
    ↓
CI
    ↓
main
    ↓
Docker images
    ↓
GHCR
```

Следующий этап развития проекта — **CD**.

В дальнейшем схема будет выглядеть примерно так:

```text
GitHub
   ↓
CI
   ↓
Docker images
   ↓
GHCR
   ↓
CD
   ↓
Server
   ↓
Training Center Platform
```

То есть после успешной сборки новая версия приложения сможет доставляться и запускаться в серверном окружении.

Эта часть будет добавлена в проект позже.

## Что студенту важно знать сейчас?

Не требуется сразу подробно разбираться во внутреннем устройстве GitHub Actions, Docker, Testcontainers, JaCoCo и SonarQube.

На данном этапе важно понимать общий процесс:

```text
Пишем код
   ↓
commit
   ↓
push в свою ветку
   ↓
Pull Request → main
   ↓
GitHub автоматически запускает CI
   ↓
Проверки должны пройти успешно
   ↓
Merge
```

Если после создания Pull Request CI стал красным — **не игнорируйте ошибку**.

Откройте GitHub Actions, найдите упавший этап и изучите лог. CI как раз нужен для того, чтобы проблема была обнаружена до попадания изменений в основную версию проекта.

Подробно устройство CI/CD и используемые инструменты будут разобраны отдельно на занятии.
